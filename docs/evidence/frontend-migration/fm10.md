## Test-first acceptance

FM10 began with route contracts and four browser acceptance scenarios. Before
implementation, the route contracts failed because neither exact route had a
React renderer, and the user-flow tests failed because neither page component
was registered. These were the expected red tests.

The first authenticated Django/PostgreSQL browser run exposed two useful local
integration defects. Django's local runserver could not discover Vite output,
so local settings now register `app/static/` as a development-only static source.
The reused synthetic candidate could also retain a failed resume from an FM9
exercise; the synthetic-only bootstrap now restores its promised clean/ready
fixture, with a regression test. Production resume validation was not weakened.

## Route and renderer boundary

The exact routes are `/jobs/` and `/roles/{opening_id}/`. Their independent
process-only development flags are `public-jobs-page` and `public-role-page`.
Committed defaults remain empty/off. Django selects either the existing legacy
template or the React template before rendering; both implementations retain
the same URL and backend operations. Disabling either flag restores that route's
legacy page without a schema change, data replay or application resubmission.

The public jobs bootstrap contains only page/version/session metadata. The role
bootstrap adds the opaque public opening identifier. Only for the authenticated
candidate may Django add that candidate's clean current resume and matching
role-consent identifiers. The signed-out HTML contains neither identifier.
React and legacy JavaScript never own the same DOM subtree.

## Public and application flow

1. `JobsDirectory` requests `GET /api/v1/public/openings?limit=25` and renders
   `JobCard` entries from the existing allowlisted public projection. It does not
   join or expose tenant, business-unit, hiring-team or internal opening data.
2. Closed, paused, expired and unpublished roles disappear because PostgreSQL's
   public projection/API remain authoritative. Empty, unavailable and retry
   states never display cached role data.
3. `RolePage` requests `GET /api/v1/public/openings/{openingId}`. Anyone may read
   the public role essentials. A disappeared role shows a safe unavailable state
   and no stale application form data is submitted.
4. `ApplicationForm`, `ResumeConsent` and `ChannelPreferences` keep typed values
   only in React memory. Nothing is copied to localStorage or sessionStorage.
5. Submission requires explicit application consent. The shared same-origin
   client supplies the CSRF token and session cookie; React adds a fresh
   idempotency key and sends the public opening ID, candidate-owned clean resume,
   role consent, motivation and selected notification preferences.
6. DRF and the service layer independently revalidate candidate authentication,
   public eligibility, internal publication linkage, resume ownership and scan/
   parse state, consent purpose/scope/audience and one-application uniqueness.
   React contains no copied authorization rule.
7. HTTP 201 is announced as Applied. Duplicate 409, session/consent denial and
   general failures are distinguished without automatic retries or duplicate
   submission.

No new API, model, migration, RLS policy, audit action, outbox operation or worker
was introduced. A successful application continues to create the existing audit,
status-event and transactional-outbox records through the established service.
