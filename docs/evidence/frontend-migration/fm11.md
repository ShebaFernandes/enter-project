## Route and rollback boundary

The exact routes are `/candidate/applications/` and `/candidate/rights/`. Their
independent process-only development flags are `candidate-progress-page` and
`candidate-rights-page`. Committed defaults remain empty/off. With a flag off,
Django renders the existing legacy page; with it on, Django renders the React
page at the same URL. Turning a flag off requires no data migration or replay.

Both server bootstraps contain only version, page and `requiresSession` fields.
Candidate, application and rights data are loaded after the shared client has
verified the session, and every API call is reauthorized by Django. Protected
data is held in React memory only; neither page uses localStorage or
sessionStorage. React and legacy JavaScript never own the same DOM subtree.

## Candidate progress flow

1. `ProgressPage` calls `GET /api/v1/candidate/applications` and renders the
   existing candidate-safe projection, including all eight candidate-facing
   status labels, published history and safe notification delivery states.
2. `StatusTimeline` never derives internal recruiting state. It displays only
   candidate statuses published by the backend.
3. `ChannelForm` first obtains the application detail and ETag, then sends the
   selected email/WhatsApp booleans with CSRF, `If-Match` and an idempotency key.
   HTTP 409 is announced without overwriting the server version.
4. `WithdrawalDialog` has a non-mutating cancel path and explains that withdrawal
   affects only the selected application. Confirmation sends `WITHDRAWN` and
   `confirm: true` with CSRF, ETag and idempotency protection.

## Privacy-rights flow

1. `RightsCenter` lists the existing rights-request projection and presents
   pending, in-progress, held, completed, failed and cancelled states without
   exposing encrypted reasons or other private implementation data.
2. Access, export, consent withdrawal and profile hiding use only the approved
   rights-request collection API. Correction returns to the candidate-owned
   profile editor rather than inventing a second editing path.
3. Completed exports use the authenticated download endpoint. The JSON response
   is converted to a short-lived object URL, downloaded, and immediately revoked;
   an unavailable/expired response is explained without showing stale data.
4. Support escalation is available only when the backend projection permits it.
   Its reason remains server-encrypted and is never returned in request history.
5. Deletion requires an accessible dialog, consequence acknowledgement and the
   recent identity-verification reference. Django still validates proof recency,
   purpose and subject binding, hides the profile immediately, and manages exact
   active-process/legal-hold exceptions.

No new API, model, migration, authorization rule, audit action, outbox operation
or worker was introduced.
